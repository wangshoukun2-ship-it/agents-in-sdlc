最初は小さな機能をプロジェクトに追加しました。より大きな変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存の開発フローに沿って動作するため、適切な方法で適切なものを構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスに従います。まず Issue から新機能を作成し、コードの妥当性と機能の動作を確認した後、プロジェクトにマージします。

> [!NOTE]
> 機能開発を続ける間は、同じセッションを使います。通常、ファイルの種類ごとに異なるセッションや PR を使いますが、ここでは主要な概念に集中するため手順を簡略化します。

このレッスンでは、次のことを行います。

- GitHub Issue からエージェントセッションを開始します。
- **Plan** モードで要件を定義します。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動で検証します。

この後のレッスンでは、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログは拡大しており、訪問者がゲームをカテゴリやパブリッシャーで絞り込める必要があります。バックログの Issue には機能が説明されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細があります。Plan モードでそのような決定を行い、範囲を明確にしたうえで Autopilot に実装を許可します。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本がさらに重要になります。多くの開発者は、次のようなフローで作業しています。

1. 実装内容が記載された Issue を開きます。
2. 構築するものの計画を立てます。
3. コードを構築してレビューします。
4. テストを実行してコードを検証します。
5. 新しい機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードレビューが完了し、継続的インテグレーション (CI) が成功したら、コードをマージします。

> [!NOTE]
> 具体的な手順はチームや組織によって異なりますが、ほとんどの場合はここに挙げた手順を応用したものです。

この標準的なアプローチに従うと、AI が生成したコードが要件を満たし、手書きのコードと同じ検証プロセスを通るようにできます。

## セッションモード

**セッションモード**では、エージェントの自律性の度合いを指定します。プロンプト欄の下にあるドロップダウンから設定でき、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、続行する前に入力を待ちます。
- **Plan**: エージェントがまず計画を作成します。実行前に計画を確認して承認します。
- **Autopilot**: エージェントが自律的に作業します。入力を待たずにコードの作成、テストの実行、反復を行います。

まず Plan モードで計画を確認し、その後 Autopilot モードで実装します。

## Issue からセッションを開始する

開始する前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys リポジトリフォルダーを選択し、リポジトリ上部のナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これは既存の Issue です。新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選択します。

    ![New session ボタンを指す矢印が表示された GitHub Copilot app の Issue ビュー](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに関連付けられていることを確認し、モード選択で **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションで見つからない場合は、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前に進め方を確認できます。Issue から開始したため、Copilot はすでに機能リクエストを把握しています。次のプロンプトを送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、計画が Issue の受け入れ条件を満たすか確認します。カテゴリとパブリッシャーによる絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認してください。複数カテゴリの組み合わせ方や、一致するゲームがない場合の動作など、曖昧な点について話し合います。

計画には、プロジェクトで既存のツールを使った lint、ユニットテスト、E2E テスト、型チェックが含まれている必要があります。フィルター機能の実装とテストに範囲を絞り、品質ワークフローを完了するまでは PR を作成しません。計画に変更が必要な場合は、承認する前に修正を依頼します。後で検証できるよう、Issue の URL と合意した明確化事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得できたら **Approve and implement this plan** または同等のオプションを選択します。承認するとモードも切り替わると決めつけず、実際に選択されているモードを確認してください。モード表示が **Autopilot** になっていることを確認します。

Copilot が実装を開始します。承認済みの計画に沿って作業を進め、コードを生成してテストを実行しながら反復する様子を確認できます。

> [!NOTE]
> 承認すると、すぐに実装が始まる場合があります。計画を先に確認してください。Copilot が依存関係の不足やポートの競合を報告した場合は、チェック完了とみなす前にセットアップの問題を解決します。自分が起動したサーバーだけを停止してください。

## 実装をレビューして検証する

生成されたコードも、他のコードと同じようにマージ前にレビューします。コードを確認し、サイトを実行して動作も確かめましょう。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリやパブリッシャーの組み合わせなど、実装が Issue と承認済みの明確化事項に沿っていることを確認します。変更が既存のリポジトリ指示に従っているかも確認してください。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。チェックのスキップは合格ではありません。
4. 不具合を解決し、影響するチェックを再実行してから実装を受け入れます。Playwright の E2E 設定はプレビューをビルドして実行し、ローカルサーバーを再利用することがあります。テスト対象が前のレッスンではなく、この worktree のサーバーであることを確認してください。

## 新機能を試す

コードに問題がないように見えても、実際に動くか確認しましょう。前回と同じようにアプリを起動し、サイトをブラウザーキャンバスで開きます。

1. 次のプロンプトを使い、Copilot にアプリの起動とブラウザーキャンバスでのページ表示を依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、GitHub Copilot app 内にブラウザーが開きます。
3. カテゴリを選択し、結果が一致することを確認します。フィルターをクリアしてからパブリッシャーを選択し、そのパブリッシャーの結果が表示されることを確認します。
4. カテゴリとパブリッシャーを組み合わせ、結果を Issue と承認済みの計画と照合します。複数カテゴリがサポートされている場合は、合意した組み合わせ動作を確認します。
5. 結果が一致しない組み合わせを試し、空の状態を確認します。フィルターをクリアまたはリセットして、全件が再表示されることも確認します。
6. 確認が終わったら、次のプロンプトで、このセッションのために起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに備えてセッションを維持する

フィルター機能の PR はまだ作成またはマージしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを維持します。次のレッスンでは、フィルターコードにカスタム指示を適用し、その後、スキルと QA の改善を追加して、レッスン 8 でまとめた PR を作成してマージします。開発サーバーを停止した後はセッションをアイドル状態にしておき、次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

異なるエージェントモードを使って機能を構築し、レビューしました。このレッスンでは、次のことを行いました。

- GitHub Issue からエージェントセッションを開始しました。
- **Plan** モードで要件を定義しました。
- **Autopilot** モードで新機能を実装しました。
- コードをレビューしました。
- ブラウザーキャンバスで機能を手動で検証しました。

次は、コードが文書化されたプラクティスに従うように、[カスタム指示を使って][next-lesson]コード生成をさらに詳しく確認します。
